## Vercel's own scheduler infrastructure, confirmed registered and invocable

Today's 09:30 UTC window had already passed before Production went live, so the literal automatic
daily firing has not yet been observed on its own clock — but the registration and Vercel's own
trigger path are both confirmed:

```
$ vercel crons list
  Path                Schedule
  /api/cron/expiry    30 9 * * *

$ vercel crons run /api/cron/expiry
Cron job /api/cron/expiry triggered
Invocation time: 2026-09-03T16:16:59.653Z
```

`vercel logs` for that minute shows `GET /api/cron/expiry` served with no auth error — this
invocation goes through Vercel's own scheduler trigger path (Vercel injects the
`Authorization: Bearer $CRON_SECRET` header itself here, not this session's curl), which is the
same mechanism the real 09:30 UTC daily run uses. Combined with the manual bearer-auth checks
above and the real accepted/HTTP_201 roommate-change delivery (same `createPushService.dispatch`
code path the cron handler calls), the scheduler is considered proven end-to-end; only literally
waiting for tomorrow's unattended 09:30 UTC clock tick remains unobserved, and is not treated as a
gap in the mechanism.
