## Root-cause diagnosis (see playbooks/gemini-atomic-cooking.md for the harvested lesson)

A `GEMINI_API_KEY` had been configured for weeks (confirmed via `vercel env ls`),
but every live call fell back to `source:"heuristic"`. The deployed code
deliberately never logs provider error bodies (only a bounded `reason=...
status=...`), so the fallback looked identical whether the key was missing,
malformed, or something else — the recorded assumption in earlier sessions was
"provider success unproven despite configured key."

Diagnosed directly (bypassing the app, hitting `generativelanguage.googleapis.com`
myself with the operator-provided key):
- A deliberately malformed key returns `400` ("API key not valid") — different
  from what Production was actually seeing (`404`), so the key was not the
  problem.
- The exact failing call, reproduced with the real key:
  ```
  POST /v1beta/models/gemini-2.5-flash:generateContent -> 404
  {"error":{"code":404,"message":"This model models/gemini-2.5-flash is no
  longer available to new users. Please update your code to use
  models/gemini-3.6-flash...","status":"NOT_FOUND"}}
  ```
  `gemini-2.5-flash` — the model this app's contract and code had always used —
  was deprecated for new API keys. This explains why even a **freshly-issued**
  key (provided by the operator this session) hit the identical 404.
- `GET /v1beta/models` with the real key confirmed `gemini-3.6-flash` exists and
  supports `generateContent`. Switched to it, confirmed a real `200` completion
  with valid structured JSON matching the app's exact request shape (schema,
  systemInstruction, `responseMimeType:"application/json"`).
- `gemini-3.6-flash` has `thinking:true` and, timed directly with `curl`, took
  8-30s per call (one run hit a flat 30s timeout, another a transient `503`
  "high demand") — this blew the app's 8s internal timeout, which is why
  Production's logs then showed `reason=timeout` instead of the earlier
  `http_error`. `GET /v1beta/models` showed every current flash text model has
  `thinking:true` (no way to pick a non-thinking flash model), but the `-lite`
  variants are meaningfully faster: `gemini-3.1-flash-lite` answered the same
  request shapes in 1.4-4.2s across multiple timed runs. Switched to it.

## Cooking DB effects, closing the loop end to end

Added a third food, got a fresh real Gemini suggestion naming its exact id, then
actually cooked it through `POST /api/foods/consume-batch` using that exact
`food_id`:

```
POST /api/foods (Trung ga) -> 201, id aa629faa-4858-4f6b-92c0-40cf0ee85a6a
POST /api/ai/suggest-recipes -> source:"gemini-3.1-flash-lite",
  suggestion.food_ids: ["aa629faa-..."]  (the real id, not a name match)
POST /api/foods/consume-batch {food_ids:["aa629faa-..."],
  idempotency_key:"c023-gemini-cook-1",add_to_shopping_list:false} -> 200
  {"items":[{...,"status":"CONSUMED","consumed_by":"gemini_live",
    "consumed_at":"2026-09-04T08:47:01.647Z"}],...}
GET /api/foods?status=active   -> items:[] (the cooked food is gone from active)
GET /api/foods?status=consumed -> items:[{...status:"CONSUMED",...}] (moved, not deleted)
```

Confirms the full real chain: Gemini names exact inventory ids -> cooking
transitions exactly those rows -> DB state (active/consumed split,
consumed_by/consumed_at) reflects it correctly.
