## Setup

Two real Chrome tabs (tab A, tab B) both authenticated into the same live room
(`512054`, `c020test`) on Production — both show "Đã kết nối" (connected) in the header,
confirming the Supabase Realtime channel actually subscribed (not degraded polling).
Tab B was instrumented in-page (`MutationObserver` on `document.body`, and a `window.fetch`
wrapper logging when the realtime-triggered `GET /api/foods` refetch fires) to get
millisecond timestamps without touching app source. Mutations were issued as authenticated
`POST /api/foods` requests (acting as "device A"); the server's own `added_date` timestamp
(ms precision) is the write's true completion time, compared against tab B's local
`Date.now()` detection time (both machine-local, real-world UTC clocks).

## Interpretation

The realtime channel genuinely subscribes (`subscribed=true` -> `transport('connected')`
per `src/services/supabaseClient.ts`), so this is not the explicit degraded-polling path
(`polling` only fires when `!subscribed`, on a 4s interval — these latencies are
consistent with a connected channel plus real end-to-end delay, not the 4s poll). The
delay sits between the Postgres write and the client's `postgres_changes` callback firing
(Supabase's WAL-based Realtime broadcast latency is the most likely source — this app's
own debounce before refetching is only 30ms, negligible against the multi-second gap) —
this session cannot inspect Supabase-side replication/broadcast internals to confirm root
cause with certainty, and does not have infrastructure access to tune it.

## Broadcast attempt (same day, after operator approval)

Implemented `supabase/realtime_broadcast.sql`: RLS SELECT policy on
`realtime.messages` scoped to the JWT's `room_code` claim, and `bump_room_sync()`
(the existing trigger, unchanged in every other respect) now also calls
`realtime.send()` with an empty payload — a fast, server-triggered "something
changed" ping, alongside the existing `room_sync_versions` row (kept as the
reliability fallback, unchanged). Client (`src/services/supabaseClient.ts`) marks
the channel `{config:{private:true}}` and adds a `.on('broadcast', {event:
'changed'}, changed)` listener next to the existing `postgres_changes` listeners
(also unchanged). 112/112 tests pass, build passes.

Applied to the live database via a temporary, secret-protected admin endpoint
(`/api/admin/migrate-c021`, since this session has no local `DATABASE_URL` — it is
a Vercel "Secret"-type var, not pullable via CLI). Verified a normal food
create+delete still worked immediately after applying. The temporary endpoint and
its `MIGRATE_SECRET` were removed and Production redeployed clean afterward
(confirmed `404` on the old route).

**Measured result across 3 post-migration runs** (server write timestamp vs. a
`window.fetch` wrapper's first `/api/foods` call, vs. DOM-visible detection):

| Run | Fetch triggered | DOM visible |
|---|---|---|
| 1 | 653 ms | 3056 ms |
| 2 | 1428 ms | 2743 ms |
| 3 | 971 ms | 3141 ms |

Compared to the pre-broadcast baseline (1231-3169ms to DOM-visible), this is
**inconclusive** — the "event received" portion may be modestly faster in some
runs, but total time-to-visible did not meaningfully improve and stayed well over
the 500ms target.

**Root cause found**: timed a single `GET /api/foods?room_code=...` directly
against Production with `curl -w '%{time_total}'`, with realtime entirely out of
the picture — **0.8-1.3 seconds for one request**. `refresh()` fires 5 such calls
in parallel (`verifyToken`, `getRoom`, `getFoods active`, `getFoods consumed`,
`getShoppingItems`), so even with instant event delivery, the refetch-and-render
cycle alone would take close to a second. This points at Vercel serverless
cold-start and/or Supabase connection-pooler latency as the dominant cost, not
the realtime transport — a different, deeper problem than "which Realtime
mechanism is used," logged as an update to this card's DEBT.md line rather than
closing it.

The broadcast change itself is kept (it is safe, purely additive, and does not
regress anything — worst case it is a no-op on top of the existing fallback), but
it alone does not close this card's Verify item 3.

## Open question for the operator (updated after the broadcast attempt)

The Broadcast-API switch (above) was implemented and applied live with the operator's
approval, but did not close the gap — the dominant cost turned out to be REST/DB
round-trip latency (0.8-1.3s per request), not the realtime transport. This card's own
Verify item still refuses done status until the target is met. Two paths remain:
1. Investigate and reduce the REST round-trip latency itself (why does a single
   `GET /api/foods` take close to a second? connection pooling, function cold-start,
   region placement between Vercel and the Supabase project) -- a genuinely different
   investigation than this card started with.
2. Accept the current latency as DEBT and correct the PRD's `<500ms` claim (F5) to
   match reality, since it is not achievable at the current infrastructure's baseline
   request latency regardless of which realtime mechanism delivers the "changed" signal.
