## Setup

Two real Chrome tabs (tab A, tab B) both authenticated into the same live room
(`512054`, `c020test`) on Production — both show "Đã kết nối" (connected) in the header,
confirming the Supabase Realtime channel actually subscribed (not degraded polling).
Tab B was instrumented in-page (`MutationObserver` on `document.body`, and a `window.fetch`
wrapper logging when the realtime-triggered `GET /api/foods` refetch fires) to get
millisecond timestamps without touching app source. Mutations were issued as authenticated
`POST /api/foods` requests (acting as "device A"); the server's own `added_date` timestamp
(ms precision) is the write's true completion time, compared against tab B's local
`Date.now()` detection time (both machine-local, real-world UTC clocks).

## Interpretation

The realtime channel genuinely subscribes (`subscribed=true` -> `transport('connected')`
per `src/services/supabaseClient.ts`), so this is not the explicit degraded-polling path
(`polling` only fires when `!subscribed`, on a 4s interval — these latencies are
consistent with a connected channel plus real end-to-end delay, not the 4s poll). The
delay sits between the Postgres write and the client's `postgres_changes` callback firing
(Supabase's WAL-based Realtime broadcast latency is the most likely source — this app's
own debounce before refetching is only 30ms, negligible against the multi-second gap) —
this session cannot inspect Supabase-side replication/broadcast internals to confirm root
cause with certainty, and does not have infrastructure access to tune it.
